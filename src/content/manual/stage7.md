# 운영 매뉴얼 — Stage 7 · 수강신청 본게임 (복합 장애 + 장애 보고서)

본 수강신청이야. 2분 30초(150초) 동안 버티면서 동시에 터지는 장애를 모두 해결해야 해.
여러 문제가 한꺼번에 오니까 대시보드를 보고 "뭐부터 고칠지"(triage) 정하는 게 핵심이야.

## 이번 단계 목표
1. 수강신청 150초 버티기 + 모든 장애 해결
2. 그다음 관제실 설계 보드에서 장애 보고서(postmortem) 작성

## 클러스터 구성 (Stage 6과 같음)
- 노드 n1~n4 (rack1~rack4). 항온항습기는 rack1·rack2 만 식혀. 노드 하나에 pod 최대 6개.
- 앱: login, course, enroll, notify. 신청(enroll) pod 하나 ≈ 1000 rps. 시작할 때 신청 pod 는 4개.

## 우선순위 판단 (triage)
1. 대시보드부터: 가용성(신청 성공률)이 얼마나 떨어졌는지, 메모(notes)에 무엇이 적혀 있는지.
2. 학생 피해가 큰 것부터: 신청 자체가 안 되는 문제 > 느려지는 문제 > 경고.
3. 곧 커질 문제도 봐: 온도가 오르는 중이면 노드가 쓰러지기 전에 막는 게 제일 싸.
4. 자동화(쿠버네티스)가 버텨주는 동안 사람은 근본 원인(케이블, 냉각)을 고쳐.

## 핵심 개념 (전체 복습)
- L1 물리 (7층 우체국의 1층 = 도로): 쿠버네티스 시대에도 케이블 한 줄이 노드를 쓰러뜨려.
- Scale-out (숫자만 바꾸면 직원이 늘어나는 매장): 접속자에 맞게 원하는 개수를 바꿔.
- 재스케줄링 · 냉각 (항공 관제사): pod 는 옮겨주지만 방은 사람이 식혀.
- 장애 보고서 · Postmortem (비유: 경기 끝나고 보는 리플레이): 무슨 일이, 왜, 어떻게 고쳤고, 다음엔 어떻게 막을지 기록해. 사람 탓이 아니라 시스템을 고치는 기록이야.

## 쓸 수 있는 명령어 (Stage 6과 같음, kubectl 을 앞에 붙여도 돼)
| 명령 | 뜻 |
|---|---|
| pods | pod 목록: STATUS, RESTARTS, NODE, VERSION, IP |
| nodes | 노드 Ready/NotReady, 랙, 온도, pod 개수 |
| deploys | 원하는 상태: READY(실제/원하는), IMAGE |
| svcs | Service 와 연결된 pod |
| scale <앱> <개수> | 원하는 pod 개수 바꾸기 |
| rollout status / history / undo <앱> | 배포 상황 / 기록 / 되돌리기 |
| set image <앱> <이미지:태그> | 새 버전 배포 |
| logs <pod 이름> | pod 로그 |
| env <앱> / env set <앱> KEY=VALUE | 설정 보기 / 바꾸기 |
| ping, ssh, exit, hostname, help, clear, hint | 공통 |

- 손으로 하는 일: 네트워크실 스위치/패치 패널(E) = 케이블 점검·교체, 냉각실 항온항습기(E) = 수리.

## 결과 읽는 법
- nodes: NotReady 인데 온도가 정상(초록)이면 → 온도가 아니라 연결(L1) 문제를 의심.
- nodes: 온도가 32°C 이상 노랑/40°C 이상 빨강이면 → 냉각 문제. 45°C 넘으면 NotReady.
- deploys/pods: 신청 Running pod × 1000 이 접속자보다 작으면 처리 부족. Pending 이 오래 남으면 노드 자리가 부족한 것.

## 장애 유형별 점검 순서
### A. 본 수강신청 트래픽 폭주
1. 대시보드: 접속자(rps)와 "신청 pod 부족: N%만 처리" 메모.
2. 필요한 pod 수 = 접속자 ÷ 1000. 지금 신청 Running pod 수와 비교.
3. 원하는 개수를 늘려. pod 가 Pending 에 머물면 NotReady 노드가 있는지 먼저 확인(노드를 살려야 자리가 생겨).

### B. 노드 하나만 NotReady (링크 다운)
1. `nodes` → 어떤 노드가 NotReady 인지, 그 노드 온도는 정상인지.
2. 온도가 정상이면 그 노드로 가는 "길"을 의심. Stage 1에서 배운 L1!
3. 네트워크실 스위치에서 그 노드 케이블 상태를 확인. 고치면 노드가 Ready 로 돌아와.

### C. 냉각 경고 (온도 상승)
1. 대시보드 온도 그래프 / `nodes` TEMP → 어느 랙이 뜨거워지는지 (항온항습기가 맡은 랙들).
2. 노드가 쓰러지기 전에 막는 게 제일 좋아. 냉각은 사람이 고쳐야 했지?
3. 냉각실 항온항습기로 가서 수리. 온도가 35°C 아래로 내려오면 노드가 돌아와.

### D. 다 고쳤는데 클리어가 안 됨
- 150초를 버텨야 해 (상단 타이머). 모든 장애가 "해결됨" 상태인지 목표 패널을 확인.
- 다 버텼으면 관제실 설계 보드에서 장애 보고서를 써야 끝나.

## 장애 보고서 쓰는 법 (보드에서)
- 무슨 일이 있었나(증상) → 왜(근본 원인) → 어떻게 고쳤나(조치) → 다음엔 어떻게 막나(재발 방지).
- 예: 케이블 → 예비 링크·정기 점검, 냉각 → 온도 경보·이중 냉각, 트래픽 → 자동 확장.
