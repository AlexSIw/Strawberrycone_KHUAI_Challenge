# 운영 매뉴얼 — Stage 5 · "내 컴퓨터에선 되는데…" (Container · Docker)

2차 수강신청 대비로 신청 서버를 늘리는 중이야. 그런데 서버마다 설치 상태가 조금씩 달라서 새 서버에서 앱이 안 떠.
앱과 실행 환경을 통째로 포장하는 컨테이너로 해결하는 단계야.

## 이번 단계 목표
1. 새 서버(srv-new)의 배포 기록 확인하기
2. 관제실 설계 보드에서 Dockerfile(레시피 카드) 완성
3. 관리 PC에서 이미지 빌드 → 레지스트리에 push
4. srv-new 에서 컨테이너 실행

## 장비
- ops: 관리 PC (이미지 빌드·push 는 여기서). 컨테이너는 없어. 컨테이너 명령(ps/logs/rm…)은 서버에 ssh 로 접속해서 써.
- srv-old: 기존 신청 서버. 신청 앱을 손으로 설치해 둬서 80번 포트를 이미 그 앱이 쓰고 있어.
- srv-new: 새 서버. srv-db: DB(MySQL) 컨테이너가 도는 서버.
- 신청 앱은 DB를 srv-db 의 3306번 포트로 찾아가. 컨테이너 이름은 상관없어.
- 서버 랙 앞(E)에서도 각 서버 콘솔을 열 수 있어.

## 핵심 개념
- 설정 차이(configuration drift) — 서버마다 설치된 프로그램 버전이 조금씩 달라서 "내 컴퓨터에선 되는데" 문제가 생겨.
- VM vs 컨테이너 — VM은 컴퓨터 통째(운영체제 포함)를 흉내 내서 무겁고, 컨테이너는 앱과 필요한 것만 묶어서 가볍고 빨라.
- 컨테이너 · 이미지 (비유: 밀키트 원본(이미지)과 그걸로 만든 한 끼(컨테이너)) — 이미지로 묶으면 어느 서버에서나 똑같이 실행돼.
- Dockerfile (비유: 레시피 카드) — 어떤 재료(FROM 베이스 이미지)로, 어디서(WORKDIR) 무엇을 넣고(COPY, RUN) 어떻게 실행할지(CMD) 적은 카드. 설계 보드의 카드 6줄이 `docker build` 에 그대로 찍혀.
- 레지스트리 (비유: 마트 냉동고) — 만든 이미지를 올려두는 곳. 다른 서버는 여기서 꺼내(pull) 써.
- 포트 매핑 -p 바깥:안쪽 (비유: 길가 문 → 주방 창구) — 컨테이너는 잠긴 방이야. 바깥(서버) 포트와, 앱이 컨테이너 안에서 실제로 기다리는 포트를 이어야 손님이 들어와. 안쪽 번호가 틀리면 문은 열려도 아무도 안 받아. Dockerfile 의 EXPOSE 는 "안쪽 창구 번호" 메모일 뿐이야. 서버의 포트 하나는 프로그램 하나만 쓸 수 있어.
- 볼륨 -v 이름:/폴더 (비유: 식당 전용 사물함) — 컨테이너 안(쓰기 레이어)에 저장한 데이터는 그 컨테이너를 지우면(rm, 새로 만들기) 함께 사라져. 재시작·stop/start 는 같은 컨테이너라 데이터가 그대로야. 프로그램이 데이터를 쓰는 폴더에 볼륨을 붙여야 컨테이너를 새로 만들어도 남아.

## 쓸 수 있는 명령어
| 명령 | 뜻 |
|---|---|
| deploy log | (그 서버에서) 손으로 한 배포 기록 보기 |
| python --version | 그 서버에 설치된 Python 버전 |
| docker build -t <이미지:태그> . | Dockerfile 로 이미지(밀키트 원본) 만들기. 레시피와 앱 코드가 있는 관리 PC 에서만 돼. 이미지 이름은 레시피 이름(enroll)과 같아야 해 |
| docker push <이미지:태그> | 이미지를 레지스트리(냉동고)에 올리기 |
| docker pull <이미지:태그> | 레지스트리에서 이미지 받아오기 |
| docker images | 이 장비에 있는 이미지 목록 |
| docker run [-p 바깥포트:안쪽포트] [-v 볼륨:/폴더] [--name 이름] [-d] <이미지> | 이미지로 컨테이너(한 끼) 실행 (서버에 접속해서). --publish, --volume, --name=x 같은 긴 형태도 돼. 옵션은 이미지 이름 앞에 |
| docker ps [-a] (= docker container ls) | 실행 중인(-a 는 멈춘 것까지) 컨테이너: IMAGE, STATUS, PORTS, VOLUME, NAME |
| docker stop <이름> / docker start <이름> | 컨테이너 멈추기 / 다시 켜기 (지우지 않아서 데이터 그대로) |
| docker restart <이름> | 같은 컨테이너 껐다 켜기 (데이터 그대로) |
| docker rm [-f] <이름> | 컨테이너 지우기 (-f: 실행 중이어도). 컨테이너 안 데이터도 같이 사라짐 |
| docker logs <이름> | 컨테이너 로그 보기 |
| docker volume create <이름> / docker volume ls | 볼륨(사물함) 만들기 / 목록. docker run -v 가 없는 볼륨은 알아서 만들어 |
| ssh, exit, hostname, help, clear, hint | 공통 |

ping 은 이 단계에서 IP 를 다루지 않아서 "이 단계에서는 장비 IP 주소를 직접 다루지 않아요"라고만 나와. 서버·컨테이너 상태는 docker ps / docker logs 로 봐.

## 결과 읽는 법
- `deploy log` 실패 예: Python 버전이 맞지 않는다는 ERROR, 모듈을 못 찾는다는 에러 → 서버 환경이 기존 서버와 달라.
- `docker build` 가 "Dockerfile(레시피 카드)이 아직 없어요" → 설계 보드에서 레시피부터. "<이름> 용 레시피는 없어요. 완성한 레시피: enroll" → 이미지 이름을 레시피 이름과 맞춰야 해. 서버에서 치면 "관리 PC에 있어요" → exit 로 관리 PC 에 돌아가서.
- `docker run` 끝의 `(바깥 N번 → 컨테이너 안 M번)`, `(볼륨 X → 컨테이너 안 /폴더)` = 방금 이은 포트와 붙인 볼륨. 맞는지는 알려주지 않아. 앱이 실제로 쓰는 번호·폴더는 docker logs 에서 비교해.
- `docker push` 가 "image does not exist locally" → 빌드부터. `docker run` 이 "레지스트리에도 없어요" → push 부터(태그까지 같은지도).
- `docker run` 이 "port is already allocated" → 그 서버의 그 바깥 포트를 이미 다른 컨테이너(또는 손으로 설치한 프로그램)가 쓰는 중. 먼저 지우거나 다른 서버에서.
- `docker run` 이 "Conflict. The container name … is already in use" → 같은 이름의 컨테이너가 이미 있음(멈춘 것 포함).
- `docker run` 이 "이 게임에서는 안 쓰는 옵션" / "이미지 이름 뒤에 쓴 … 는 컨테이너 안에서 실행할 명령" → 옵션 철자나 순서 확인.
- `docker ps` 의 PORTS: `0.0.0.0:<바깥>-><안쪽>` 이면 이어진 것. `(없음)` 이면 밖에서 못 들어와. 안쪽 번호가 앱이 기다리는 번호와 다르면 이어져도 아무도 안 받아.
- `docker ps` 의 VOLUME: `-` 이면 데이터가 컨테이너 안에만 있음(지우면 사라짐).
- `docker logs <신청 앱 컨테이너>`: "Running on http://0.0.0.0:<번호>" = 앱이 컨테이너 안에서 기다리는 번호. "DB srv-db:3306 연결 실패" = DB 를 못 찾음.
- `docker logs <DB 컨테이너>`: "Table enrollments is empty" 경고 = 빈 DB. data dir 줄이 "(컨테이너 안 · 컨테이너를 지우면 함께 사라짐)"이면 데이터가 볼륨에 없는 것, "→ volume:<이름>"이면 볼륨에 있는 것. "볼륨(X)은 /경로 에 붙어 있음"이면 볼륨을 data dir 이 아닌 다른 폴더에 붙인 것.
- 대시보드 "DB 응답 없음 (신청 앱 → srv-db:3306)" → srv-db 에 3306번으로 열린 DB 컨테이너가 없음(꺼졌거나, 포트를 안 열었거나, 다른 서버에 띄웠거나).

## 장애 유형별 점검 순서
### A. 새 서버에서 앱이 안 뜸 (환경 차이)
1. srv-new 에 접속해서 `deploy log` → 어떤 에러인지 읽어.
2. `python --version` 을 srv-old 와 srv-new 에서 비교해봐. 다르지?
3. 서버마다 맞춰 깔기보다 앱+환경을 통째로 포장(이미지)하는 쪽으로.
4. 순서: 레시피(설계 보드) → 빌드 → 냉동고에 올리기 → 새 서버에서 꺼내 실행.

### B. 컨테이너는 Up 인데 접속 불가 (포트 매핑)
1. 그 서버에서 `docker ps` → STATUS 는 Up 인데 PORTS 칸이 비었는지, 또는 안쪽 번호가 뭔지 봐.
2. `docker logs` 로 앱이 컨테이너 안 몇 번에서 기다리는지 확인하고 PORTS 의 안쪽 번호와 비교해. 학생은 웹 기본 포트(길가 문)로 와.
3. 실행 옵션에 바깥 문과 안쪽 창구를 잇는 설정이 있었어. 이미 뜬 컨테이너는 포트를 바꿀 수 없어서 지우고 다시 실행해야 해. (바깥 포트가 이미 쓰이는 중이면 "port is already allocated" 가 나와.)

### C. 컨테이너를 새로 만들었더니 데이터 0건 (볼륨)
1. 대시보드: "신청 내역 0건! 데이터 유실". DB 업데이트 스크립트가 DB 컨테이너를 지우고 새로 만들었어(CONTAINER ID 가 바뀌어 있어).
2. srv-db 에 접속해서 DB 컨테이너 로그 → data dir 이 컨테이너 안이었는지 확인.
3. `docker ps` 의 VOLUME 칸이 `-` 이면 사물함 없이 쓰고 있던 것.
4. 사물함(볼륨)을 DB 의 data dir 폴더에 붙여서 DB 컨테이너를 새로 실행하면 어젯밤 백업이 그 빈 볼륨으로 복원돼. 신청 앱이 찾아오는 포트(srv-db 의 3306)도 그대로 열어야 해. 옛 DB 컨테이너가 그 포트·이름을 잡고 있으면 먼저 지워. 컨테이너 이름과 볼륨 이름은 아무거나 괜찮아.
5. 재시작(restart)이나 stop/start 로는 해결 안 돼. 같은 컨테이너라 지금 빈 데이터가 그대로야.

## 힌트 줄 때 참고
- 포트 숫자 쌍이나 볼륨 옵션(볼륨:폴더) 같은 완성 옵션은 말하지 마. "PORTS/VOLUME 칸을 봐", "앱 로그가 말하는 번호와 비교해봐", "로그의 data dir 을 봐", "실행 옵션 중에 잇는 게 있어" 정도로.
- 밀키트 → 냉동고 → 한 끼, 사물함 비유를 이어가.
