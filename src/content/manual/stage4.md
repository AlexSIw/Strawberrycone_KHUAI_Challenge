# 운영 매뉴얼 — Stage 4 · 1차 수강신청 대란 (모놀리스 → MSA)

1차 수강신청 날이야. 접속자가 평소의 50배. 기능이 전부 한 프로그램에 들어 있는 "모놀리스" 앱이 버틸 수 있을까?
관리 PC 터미널에서 svc 명령으로 서비스 상태를 지켜봐. 관제실 설계 보드에서는 서비스를 어떻게 나눌지 설계해.

## 이번 단계 목표
1. 관리 PC 터미널에서 svc list 로 서비스 상태 확인
2. 그다음부터는 장애가 연달아 와. 하나씩 해결하면 클리어.

## 핵심 개념
- 모놀리스 → MSA (비유: 주방 하나인 큰 식당 → 매장들이 모인 푸드코트) — 모든 기능이 한 덩어리면 한 기능(예: 알림 메일)의 버그에도 전체가 멈춰. 기능(업무)별로 나누면 그 매장만 문을 닫아. 나눌 때는 "업무 단위(business capability)"로 잘라. 화면/로직/DB 같은 층으로 자르면 안 돼.
- 장애 격리 (비유: 리뷰 매장이 문 닫아도 주문은 된다) — 한 서비스가 죽어도 다른 서비스로 번지지 않아.
- 독립 확장 (비유: 붐비는 매장만 직원 추가) — 바쁜 서비스만 골라서 늘릴 수 있어. 하지만 지금은 서버를 손으로 깔아서 한 대에 몇 초씩 걸려.
- DB는 서비스마다 따로 (비유: 남의 매장 창고에 몰래 들어가지 않기) — 다른 서비스의 DB를 직접 읽으면 나눠놓고도 다시 한 덩어리(분산 모놀리스). 서비스끼리는 API(카운터에 주문)로만 대화해.
- "공짜 점심은 없다" — 나누면 격리·확장을 얻지만 네트워크 호출과 운영할 게 늘어나. 모놀리스가 나쁜 건 아니야(Monoliths are not evil). 상황에 맞게 골라.

## 서비스 (분리 후)
login(로그인) · course(과목조회) · cart(장바구니) · enroll(수강신청) · notify(알림). 분리 전에는 monolith 하나.

## 쓸 수 있는 명령어
| 명령 | 뜻 |
|---|---|
| svc list | 서비스별 상태(up/DOWN), 서버 수, 처리 용량(rps), 설치 중인 서버 수, 현재 접속자와 구조(모놀리스/MSA) |
| svc restart <서비스> | 그 서비스만 재시작 |
| svc scale <서비스> <서버 수> | 그 서비스의 서버 수를 그 숫자로 맞추기 (손으로 설치라 한 대에 몇 초씩, 한 대씩 차례로). 설치 중에 숫자를 낮추면 남은 설치가 취소돼 |
| svc deps <서비스> | 그 서비스가 부르는 API와 직접 읽는 DB 목록 (남의 DB면 ⚠ 경고) |
| svc config <서비스> course-source api\|db | 과목 정보를 과목조회 API로 받을지, DB에서 직접 읽을지 |
| ping, ssh, exit, hostname | 공통 네트워크 도구 |
| help, clear, hint | 공통 |

- 관제실 설계 보드(E): 모놀리스 기능 카드를 서비스로 묶는 퍼즐. 업무 단위로 묶어야 통과해.

## 결과 읽는 법
- `svc list` 의 STATE: up(초록) / DOWN(빨강). CAPACITY 는 "서버 수 × 서버 한 대 용량". 접속자(rps)보다 작으면 과부하.
- 대시보드 서비스 맵: 초록 = 정상, 노랑 = 과부하(degraded), 빨강 = 다운.
- 대시보드 가용성 = 신청 성공률. 어떤 서비스가 죽었을 때 이 숫자가 같이 떨어지는지 보면 장애가 번졌는지 알 수 있어.

## 장애 유형별 점검 순서
### A. 전체 다운 (모놀리스의 한계)
증상 예: "시작 1분 만에 서버 전체 다운! 알림 메일 기능에서 에러"
1. `svc list` → monolith 하나가 DOWN, 구조는 모놀리스.
2. 재시작해봐도 몇 초 뒤 또 죽어 → 버그가 그대로라 재시작은 임시방편.
3. 생각할 질문: 알림 기능 하나 때문에 왜 로그인·과목조회·신청까지 멈출까? → 한 덩어리라서.
4. 근본 해결은 구조를 바꾸는 것. 관제실 설계 보드에서 업무 단위로 나눠봐.

### B. 한 서비스만 다운 (장애 격리 확인)
증상 예: "알림 서비스가 또 죽었는데… 신청은 계속 돼요?"
1. 대시보드 가용성: 아까와 달리 신청 성공률이 유지되는지 봐. → 격리 성공의 증거.
2. `svc list` 로 DOWN 인 서비스가 무엇인지 확인.
3. 이제 그 매장만 손보면 돼. 알림팀이 핫픽스를 올렸으니 그 서비스만 다시 시작하면 반영돼.

### C. 한 서비스만 느림 (과부하)
증상 예: "모두가 빈자리 새로고침 중! 과목조회가 느려지면서 신청까지 버벅여요"
1. 대시보드 서비스 맵에서 노란불인 서비스를 찾아. 모든 서비스가 바쁜 건 아니야.
2. `svc list` 로 그 서비스의 CAPACITY 와 수요를 비교.
3. 그 서비스만 서버 수를 늘려. 설치 중(+N 설치중)이 사라질 때까지 기다려야 해.
4. 느리지? 손으로 설치하는 방식의 한계야. → 다음 단계(컨테이너)의 동기.

### D. 남의 DB 구조가 바뀌었는데 내 서비스가 터짐 (분산 모놀리스)
증상 예: "과목팀이 과목 DB 구조를 바꿨는데 왜 신청 서비스가 터져요?"
1. 터진 서비스에 대해 `svc deps <서비스>` → DB 접근 목록에 남의 DB(⚠ 경고)가 있는지 봐.
2. 남의 창고에 직접 들어가 재료를 가져오고 있었다면, 창고 배치가 바뀌면 바로 망가져.
3. 창고 대신 그 매장 카운터(API)에 주문하도록 설정을 바꾸는 게 해결 방향.

## 힌트 줄 때 참고
- 서비스 이름과 숫자를 붙인 완성 명령은 말하지 마. "어떤 명령으로 무엇을 비교할지"만.
- 식당 → 푸드코트 비유를 계속 이어가면 이해가 쉬워.
