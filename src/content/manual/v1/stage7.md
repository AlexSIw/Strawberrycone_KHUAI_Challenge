# 운영 매뉴얼 — Stage 7 · 수강신청 본게임 (복합 장애 + 장애 보고서)

본 수강신청이야. 2분 30초(150초) 동안 버티면서 동시에 터지는 장애를 모두 해결해야 해.
여러 문제가 한꺼번에 오니까 대시보드를 보고 "뭐부터 고칠지" 정하는 게(triage, 우선순위 판단) 핵심이야.

## 이번 단계 목표
1. 수강신청 150초 버티기 + 모든 장애 해결
2. 그다음 관제실 설계 보드에서 장애 보고서(postmortem, 장애가 끝난 뒤 쓰는 기록) 작성 (보드는 150초가 지나고 장애가 다 끝나야 열려. 그 전에 낸 보고서는 안 쳐줘)

## 클러스터 구성 (Stage 6과 같음)
- 노드(일하는 서버) n1~n4 (rack1~rack4). 항온항습기(CRAC)는 rack1·rack2 만 식혀. 노드 하나에 pod 최대 6개.
- 앱: login, course, enroll, notify. 신청(enroll) pod 하나가 1초에 요청 약 1000건(1000 rps)을 처리해. rps = 1초에 들어오는 요청 수. 시작할 때 신청 pod 는 4개.

## 우선순위 판단 (triage)
1. 대시보드부터: 가용성(신청 성공률)이 얼마나 떨어졌는지, 메모(notes)에 무엇이 적혀 있는지.
2. 학생 피해가 큰 것부터: 신청 자체가 안 되는 문제 > 느려지는 문제 > 경고.
3. 곧 커질 문제도 봐: 온도가 오르는 중이면 노드가 쓰러지기 전에 막는 게 제일 싸.
4. 자동화(쿠버네티스)가 버텨주는 동안 사람은 근본 원인(케이블, 냉각)을 고쳐.

## 핵심 개념 (지금까지 나온 것 모아보기)
- L1 물리 연결 (7층 우체국의 1층 = 도로): 쿠버네티스 시대에도 케이블 한 줄이 노드를 쓰러뜨려.
- Scale-out(옆으로 늘리기) (숫자만 바꾸면 직원이 늘어나는 매장): 접속자에 맞게 원하는 개수를 바꿔.
- 재스케줄링(다른 자리에 다시 배치) · 냉각: 노드가 쓰러지면 쿠버네티스가 살아 있는 노드에 새 pod 를 띄워주지만(옮기는 게 아니라 새로 태어남), 방은 사람이 식혀.
- 장애 보고서 · Postmortem (비유: 경기 끝나고 보는 리플레이): 무슨 일이, 왜, 어떻게 고쳤고, 다음엔 어떻게 막을지 기록해. 사람 탓이 아니라 시스템을 고치는 기록이야.

## 쓸 수 있는 명령어 (Stage 6과 같음, kubectl 을 앞에 붙여도 돼)
| 명령 | 뜻 |
|---|---|
| pods | pod 목록: STATUS, RESTARTS, AGE, NODE, VERSION, IP |
| nodes | 노드 Ready/NotReady, 랙, 온도, pod 개수 |
| deploys | 원하는 상태: READY(실제/원하는), IMAGE |
| svcs | Service 와 연결된 pod |
| scale <앱> <개수> | 원하는 pod 개수 바꾸기 (`scale deployment <앱> --replicas=N` 도 돼) |
| rollout status / history / undo <앱> | 배포 상황 / 기록 / 되돌리기 |
| set image <앱> <앱:태그> | 다른 버전 배포 |
| logs <pod 이름> | pod 로그 |
| env <앱> / env set <앱> KEY=VALUE | 설정 보기 / 바꾸기 |
| ssh, exit, hostname, help, clear, hint | 공통 (ping 은 이 단계에선 안 써. 노드 상태는 nodes 로 봐) |

- 손으로 하는 일: 네트워크실 스위치/패치 패널(E) = 케이블 점검·교체, 냉각실 항온항습기(E) = 수리.

## 결과 읽는 법
- nodes: NotReady(일할 수 없는 상태)인데 온도가 정상(초록)이면 → 온도가 아니라 연결(L1) 문제를 의심.
- nodes: 온도가 32°C 이상 노랑/40°C 이상 빨강이면 → 냉각 문제. 45°C 넘으면 NotReady.
- deploys/pods: 신청 Running pod × 1000 이 접속자보다 작으면 처리 부족.
- pods: Pending(대기 중)인데 NODE 가 `<none>` 이면 들어갈 노드 자리가 없는 것(목록 아래 "0/4 nodes are available: NotReady N대…" 설명). deploys READY 도 원하는 개수에 못 미쳐. 노드를 살리면 기다리던 pod 가 자동으로 자리를 잡아.

## 장애 유형별 점검 순서
### A. 본 수강신청 트래픽 폭주
1. 대시보드: 접속자(rps)와 "신청 pod 부족: N%만 처리" 메모.
2. 필요한 pod 수 = 접속자 ÷ 1000. 지금 신청 Running pod 수와 비교.
3. 원하는 개수를 늘려. pod 가 Pending(NODE `<none>`)에 머물면 NotReady 노드가 있는지 먼저 확인(노드를 살려야 자리가 생겨).

### B. 노드 하나만 NotReady (링크 다운)
1. `nodes` → 어떤 노드가 NotReady 인지, 그 노드 온도는 정상인지.
2. 온도가 정상이면 그 노드로 가는 "길"(장비끼리 실제로 이어진 물리 연결, L1)을 의심. Stage 1 때 일을 떠올리게 해.
3. 네트워크실 스위치에서 그 노드 케이블 상태를 확인. 고치면 노드가 Ready 로 돌아와.
- 장애 알림은 증상(n3 NotReady, pod 사라짐)만 알려줘. 케이블이 원인이라는 건 플레이어가 온도와 비교해서 알아내야 해. 1단계 힌트에서 먼저 말하지 마.

### C. 1·2번 랙 온도 상승 (냉각 문제)
1. 대시보드 온도 그래프 / `nodes` TEMP → 어느 랙이 뜨거워지는지 (항온항습기가 맡은 랙들).
2. 노드가 쓰러지기 전에 막는 게 제일 좋아. 냉각은 사람이 고쳐야 했지?
3. 냉각실 항온항습기로 가서 수리. 온도가 35°C 아래로 내려오면 노드가 돌아와.
- 해결 조건: 항온항습기 수리 + 그 항온항습기가 식히는 랙(rack1·rack2)의 노드가 Ready. n3 는 냉각과 상관없어서, n3 케이블이 아직 끊겨 있어도 이 온도 장애는 닫혀.

### D. 학생 민원 폭주 (서비스 붕괴 경보, 나올 수도 안 나올 수도)
- 다른 장애를 오래 쌓아둬서 신청 성공률이 30% 아래로 떨어지고, 쿠버네티스가 혼자 회복할 수도 없을 때(새로 뜨는 중인 pod 도 없음) 뜨는 경보야. 게임 오버는 아니야.
- 따로 고칠 장치는 없어. 남은 장애(신청 pod 개수, 쓰러진 노드)를 끝내서 성공률이 90% 이상으로 돌아오면 닫혀.
- 1단계 힌트: 대시보드 메모를 읽게 해. 2단계: 노드 자리와 pod 개수 둘 다. 3단계: nodes / deploys 로 하나씩 확인.

### E. 다 고쳤는데 클리어가 안 됨
- 150초를 버텨야 해 (상단 타이머). 모든 장애가 "해결됨" 상태인지 목표 패널을 확인. 학생 민원 폭주 경보가 떠 있으면 그것도 닫혀야 해.
- 다 버텼으면 관제실 설계 보드에서 장애 보고서를 써야 끝나.

## 장애 보고서 쓰는 법 (보드에서)
- 무슨 일이 있었나(증상) → 왜(근본 원인) → 어떻게 고쳤나(조치) → 다음엔 어떻게 막나(재발 방지).
- 예: 케이블 → 예비 링크·정기 점검, 냉각 → 온도 경보·이중 냉각, 트래픽 → 자동 확장.

## 쉬운 말 풀이 (용어를 처음 쓸 때 같이 말해줘)
- rps = 1초에 들어오는 요청 수. 노드 = 일하는 서버. pod = 앱이 실제로 돌아가는 가장 작은 단위.
- Ready / NotReady = 노드가 일할 수 있음 / 없음. Pending = 아직 준비 안 됨(자리를 기다리는 중).
- triage = 피해가 큰 것부터 고르는 우선순위 판단. postmortem = 장애가 끝난 뒤 쓰는 장애 보고서. L1 = 맨 아래층, 장비끼리 실제로 이어진 물리 연결.

## 힌트 줄 때 참고
- 이번엔 힌트를 아끼라고 했어. 짧게, 다음에 볼 곳 하나만.
