# 운영 매뉴얼 — D-Day · 수강신청 당일 (실시간 관제 · triage · 장애 보고서)

수강신청 날이야. 오늘은 새로 만드는 게 없어. 5일 동안 만든 데이터센터를 지켜보다가, 터지면 막아.
시계는 09:50에 시작해서 10:30 1차 마감까지 가. 사람이 몰리는 동안은 시계가 느리게 가(타이핑할 시간을 주려고).
경보가 한꺼번에 여러 개 뜰 수 있어. "뭐부터 고칠지" 정하는 게(triage, 우선순위 판단) 오늘의 핵심이야.
터미널은 관제실 관리 PC(책상)에서 열어. 다른 장비는 관리 PC에서 ssh <이름> 으로 들어가.

## 이번 날 목표
1. 점검 ① 관제 화면(NMS)을 열어 열린 경보가 없는지 확인하기
2. 점검 ② 코어 스위치에서 게이트웨이 이중화 상태 보기 (show standby brief)
3. 점검 ③ L4(접속을 서버들에 나눠 주는 장비)에서 세션(지금 붙어 있는 접속) 수와 서버 상태 보기 (lb status)
4. 10:30 1차 마감까지 수강신청 지키기 (10:30이 지나고, 학생들이 정상으로 신청하고 있고, 매크로가 막혀 있고, 오늘 뜬 장애가 다 해결돼야 완료)
5. 관제실 설계 보드에서 장애 보고서 쓰기 (10:30 마감 뒤에 열려)

## 오늘의 데이터센터 (D-Day 아침 = 5일 동안 만든 전부)
학생 → 인터넷 → 경계 라우터(BR) → 방화벽(FW-01) → 코어(CORE-01 · CORE-02, HSRP 이중화) → L4-01 (대표 주소 sugang = 10.10.30.100)
→ 쿠버네티스 노드 n1~n4 의 30080 포트(NodePort) → 신청(enroll) pod
- n1 · n2 는 2번 랙, TOR-01 아래. TOR-01 은 코어로 가는 10G 선 두 가닥을 묶어(Po1, LACP) 20G로 써.
- n3 · n4 는 3번 랙, TOR-02 아래. TOR-02 는 코어(CORE-01)로 가는 선이 10G 한 가닥이야. 같은 CORE-01 로 가는 예비 선이 꽂혀는 있지만 꺼져 있어.
- TOR-02 의 CORE-02 쪽 선(UPLINK-CORE-02)은 STP 가 막아 둔 비상용 길이야. 코어 두 대는 서로 따로 노는 장비(HSRP로 짝만 맞춤)라서, 서로 다른 코어로 가는 선끼리는 한 묶음(LACP)으로 못 묶어.
- CORE-01 은 TOR-01 과의 묶음에 이미 Po1 을 쓰고 있어. 한 장비 안에서 묶음 번호 하나는 한 상대하고만 묶이니까, 새 묶음엔 그 장비에서 아직 안 쓰는 번호를 써.
- L4는 학생 요청을 노드마다 그 노드에 있는 신청 pod 수만큼 나눠 보내.
- 신청 pod(신청 앱이 돌아가는 작은 실행 단위) 하나는 1초에 1000건쯤 처리해. 아침엔 4개. 노드 하나에 pod 6개까지, 노드 4대 = 24자리이고 다른 앱(login · course · notify)이 5자리를 써. scale 명령은 앱 하나를 최대 16개까지만 늘려 줘(더 큰 수를 넣어도 16으로 맞춰져).
- 신청 pod들은 원래 신청 DB인 DB-01 을 써(D-2의 DB-02 는 APP-01 시험 서버용이었어). 신청 pod 하나는 DB-01 과 연결을 미리 열어 둬(커넥션 풀, 환경변수 DB_POOL, 아침 값 20). DB-01 은 동시에 연결 200개까지만 받아.
- L4 세션 표(동시에 붙잡을 수 있는 손님 자리)는 30000. 학생 요청 하나가 2초쯤 자리를 차지해서, 세션 수 ≈ (1초 요청 수) × 2.
- 관제 화면(NMS)의 사용률 순찰(SNMP 폴링)은 오늘 10초마다 돌아.

## 우선순위 판단 (triage)
1. 경보가 뜨면 먼저 확인(ACK). "누가 보고 있다"는 표시이자 MTTD(탐지 시간)가 멈추는 순간이야.
2. 등급 순서대로: Critical(학생이 신청을 아예 못 하거나 오류가 남) → Major(느리거나 일부만 실패, 이중화가 깨짐) → Minor → Warning.
3. 같은 등급이면 피해 범위가 넓은 것부터. 관제 화면 SMS 의 수강신청 가용성(성공률)과 메모(notes)를 봐.
4. 하나를 고치면 다른 데가 터질 수 있어. 고친 직후엔 가용성과 새 경보를 꼭 다시 봐.
5. 전화 제보가 NMS 경보보다 먼저 올 수도 있어. 사용률·응답시간 같은 숫자 경보는 다음 순찰 때에야 뜨거든.

## 핵심 개념
- 트래픽 피크 · 병목 (비유: 명절 고속도로, 가장 좁은 구간이 전체 속도를 정한다) — 평소의 수십 배가 한순간에 몰리는 때가 피크야. 가장 먼저 꽉 차는 곳(병목)이 전체를 정해. 한 곳을 넓히면 그다음 좁은 곳이 병목이 돼: pod → DB → 링크 순서로 차례차례 볼 것.
- 접속 대기열 · 연결 한도 (비유: 맛집 앞 번호표 · 식당 좌석 수) — L4 · 서버 · DB 는 동시에 붙잡을 수 있는 연결 수(좌석)가 정해져 있어. 다 차면 새 손님은 거절돼. 수강신청 대기열 화면은 감당할 만큼만 순서대로 들여보내는 장치야.
- Scale-out (비유: 숫자만 바꾸면 직원이 늘어나는 매장) — 원하는 pod 개수만 바꾸면 쿠버네티스가 알아서 늘려. 노드에 빈자리가 있어야 해.
- LACP · 링크 묶기 (D-2에 해본 것) — 같은 두 장비 사이 선 여러 가닥을 하나로 묶어(포트 채널) 용량을 더하고, 한 가닥이 끊겨도 버텨. 양쪽 끝 장비 모두에 같은 묶음 설정을 해야 묶여. 그냥 선만 하나 더 켜면 STP(고리 방지)가 하나를 막아서 용량은 그대로야.
- 매크로 · 방화벽 (비유: 입구 경비) — 사람은 주소 하나당 20초에 한 번쯤(0.05) 누르지만 매크로(자동 클릭 프로그램)는 1초에 수십 번 눌러. 방화벽은 출발지별 요청 수를 보고, 수상한 출발지 대역만 골라 막을 수 있어. 너무 넓게 막으면 학생도 막혀.
- MTTD · MTTR — MTTD = 장애 시작 → 경보 확인(ACK)까지, MTTR = 장애 시작 → 복구까지. 일일 리포트와 장애 보고서에 나와.
- 장애 보고서 · Postmortem (비유: 경기 끝나고 보는 리플레이) — 무슨 일이, 언제, 왜 일어났고, 어떻게 고쳤고, 다음엔 어떻게 막을지 남겨. 사람 탓이 아니라 시스템을 고치는 기록이야.

- SMS: 수강신청 가용성, 응답시간, 앱별 상태, 메모(notes).
- 설계 보드(E): 10:30 마감 뒤 장애 보고서.

## 장애 유형별 점검 순서
### A. 오픈 직후 페이지가 안 열림 (신청 pod 부족) · Critical
증상 예: "수강신청 페이지가 안 열려요! 겨우 들어가도 화면이 빙글빙글 돌기만 해요…" · 경보 "L4-01 서버 풀 응답시간 급증"
1. SMS: 접속량(rps)이 얼마나 뛰었는지, 메모에 "신청 pod 부족: N%만 처리"가 있는지.
2. deploys / pods: 신청(enroll) Running pod 수 × 1000 과 지금 접속량을 비교.
3. 필요한 개수 = 접속량 ÷ 1000 (10:05 신청 집중엔 더 몰려오니 여유 있게). scale 은 최대 16개까지야.
4. 해결 방향: 원하는 pod 개수를 늘리기(scale). 몇 초 뒤 pods 에서 Running 확인, SMS 가용성 확인. 오픈 피크를 받을 만큼 늘려야 경보가 꺼져(10:20 넘어 접속이 줄어도 그대로면 안 꺼져).
- 다음에 올 일: pod를 많이 늘리면 B 가 따라올 수 있어. 늘린 직후 경보를 계속 봐.

### B. 신청 버튼 누르면 오류 (DB 연결 한도 초과) · Critical
증상 예: "신청 버튼 누르면 에러가 나요! '잠시 후 다시 시도해 주세요'만 떠요." · 경보 "DB-01 동시 연결 수 한도 도달 (200/200)"
1. 언제부터? 대개 pod를 늘린 직후야. 늘어난 pod들이 함께 쓰는 게 뭔지 생각해.
2. env enroll 로 pod 하나가 여는 DB 연결 수(DB_POOL)를 확인. pod 수 × 그 값 > 200 이면 자리를 못 잡은 요청이 오류가 나.
3. 해결 방향: pod 수는 그대로 두고, pod 하나가 여는 연결 수를 줄이기(env set). pod 수 × 새 값 ≤ 200 이 되게.
- pod 수를 다시 줄여도 오류는 멎지만, 그러면 A 가 다시 터져. 그건 해결이 아니야.

### C. 신청은 되는데 느리고 가끔 튕김 (랙 스위치 업링크 포화) · Major
증상 예: "신청은 되는데 너무 느려요… 몇 번씩 눌러야 겨우 돼요." · 경보 "TOR-02 업링크 사용률 100% 초과"
1. NMS 지도: 빨간 선이 어디야? TOR-02 ↔ CORE-01 이 100%를 넘고, TOR-01 쪽 묶음은 여유가 있어.
2. TOR-01 과 TOR-02 에서 show etherchannel summary 비교: TOR-01 은 두 가닥이 묶여 있고(Po1), TOR-02 는 묶음이 없어.
3. TOR-02 에서 show interfaces status: 꽂혀만 있고 꺼진(disabled) 예비 업링크가 있어(설명 칸 참고). 그 선의 반대쪽은 CORE-01 이야. CORE-02 로 가는 선(STP 가 막아 둔 비상용 길)은 다른 코어라서 같이 못 묶어.
4. 해결 방향: TOR-02 의 CORE-01 쪽 두 업링크 포트를 같은 묶음(LACP)에 넣고 꺼진 포트를 켠다. CORE-01 쪽 두 포트도 똑같이. 양쪽 다 해야 묶여. CORE-01 은 Po1 을 TOR-01 묶음에 쓰고 있으니 새 번호로! show etherchannel summary 에서 (SU)·(P) 확인하고 저장.
- (s) 가 뜨면: 반대쪽 설정이 빠졌거나, 이미 다른 상대와 묶인 번호에 넣었거나, 다른 코어로 가는 선을 섞은 거야. no channel-group 으로 빼고 다시 넣으면 돼.
- 신청 집중 피크를 받을 만큼 넓혀야 경보가 꺼져(10:20 넘어 접속이 줄어도 그대로면 안 꺼져).
- 선만 켜고 묶지 않으면 STP 가 하나를 막아서 그대로야. pod를 TOR-01 쪽 노드로만 몰아도 TOR-01 묶음(20G)이 혼자 다 못 받아.

### D. 사람은 줄었는데 다시 접속 거부 (매크로가 L4 세션을 차지) · Critical
증상 예: "또 접속이 안 돼요! '접속자가 너무 많습니다'만 떠요. 아까보다 사람은 줄었다는데요?" · 경보 "L4-01 세션 테이블 가득 참"
1. lb status: 세션이 한도(30000)에 붙어 빨강. 그런데 학생 접속량 × 2 보다 훨씬 많아. (10:20 넘어 학생이 줄어도, 매크로가 빈자리를 채워서 막을 때까지 그대로야.)
2. ssh FW-01 → fw top: 주소 하나당 요청 수(RPS/ADDR)가 사람(0.05)의 수백 배인 출발지 줄을 찾아. 학생 대역(175.223 · 211.234 · 59.10)과 구분해.
3. 해결 방향: 그 출발지 대역만 막는 규칙을 넣기(fw deny). fw top 에서 BLOCKED 로 바뀌고 lb status 세션이 내려오는지 확인.
- 학생 대역이나 아주 넓은 범위(/8 같은)를 막으면 학생도 못 들어와. 학생 대역이 하나라도 막혀 있으면(fw top 의 FW 칸이 BLOCKED) 이 장애는 안 끝나. 잘못 넣었으면 fw rules 에서 SEQ 를 보고 fw del.

### E. 다 고쳤는데 끝나지 않음
- 점검 ①②③ 을 했는지 목표 패널 확인 (10시 이후에도 할 수 있어).
- 10:30 이 지나야 해. 그때 수강신청 가용성이 정상이고, 매크로 출발지가 막혀 있고, 오늘 뜬 장애가 다 해결돼 있어야 "지키기"가 완료돼.
- 접속이 줄어 그래프가 멀쩡해 보여도 경보가 남아 있으면, 그 장애의 원인은 아직 그대로야. A · C 를 다시 봐.
- 그다음 설계 보드에서 장애 보고서를 써서 제출해야 끝나.

## 장애 보고서 쓰는 법 (설계 보드)
- 오늘 일어난 장애가 일어난 순서대로 나와. 장애마다 발생 시각 → 확인(ACK) 시각(MTTD) → 해결 시각(MTTR).
- 칸마다 하나씩: 원인(왜?) → 조치(실제로 한 일) → 재발 방지(다음엔 어떻게 막을까). 원인·조치가 틀리면 빨갛게 표시돼.
- 예: pod 부족 → 피크 전에 미리 늘리기·오토스케일링, DB 한도 → 늘리기 전에 pod 수 × 연결 수 계산, 업링크 → 처음부터 두 가닥 묶기·사용률 경보, 매크로 → 주소당 요청 수 제한·캡차.
- 사람 탓을 쓰는 문서가 아니야. "시스템이 어떻게 바뀌면 다시 안 터질까"를 쓰는 거야.

## 힌트 줄 때 참고
- 경보가 여러 개면 먼저 "지금 학생이 신청을 아예 못 하고 있어?"를 물어서 Critical 부터 고르게 해줘.
- pod 개수, DB_POOL 값, 포트 이름(Te…), 포트 채널 번호, 매크로 출발지 주소 같은 정답 값은 말하지 마. 명령은 값만 빈칸으로 둔 모양(scale <앱> <개수>, env set <앱> DB_POOL=<값>, fw deny <주소/길이>)으로 알려줘도 되고, 무엇과 무엇을 비교할지(접속량 vs pod × 1000, pod 수 × 연결 수 vs DB 한도, TOR-01 vs TOR-02 묶음, 주소당 요청 수)를 같이 짚어줘.
- C 는 D-2 에 한 포트 묶기를 떠올리게 해줘. 양쪽 장비 모두에 해야 한다는 점, 꺼진 포트는 켜야 한다는 점까지는 말해도 돼.
- D 는 fw top 으로 출발지별 순위를 보고 fw deny <주소/길이> 로 막아. 어느 줄인지는 플레이어가 RPS/ADDR 로 찾게 해.
- 플레이어는 서버를 처음 접하는 일반인이야. rps, pod, 세션, LACP, 매크로 같은 말은 처음 쓸 때 쉬운 말로 한 번 풀어줘.
